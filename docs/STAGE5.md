# AEO Intelligence OS — Direct Client AEO Operations v1.0

## 1. 기존 1~4단계 점검

고객·질문·불변 응답 원문, 업체 식별/검토, 수동 소비자 화면 관측, CSV/JSON, 증빙 첨부, 공개 홈페이지 검사, 경쟁사 격차 진단, 내부 우선순위, 개선 작업, 동일 조건 재측정 기능을 재사용했다. 기존 데이터베이스를 초기화하지 않았다. 실제 소비자 측정 결과가 없는 프로젝트는 미측정으로 표시한다. 과거 API 오류 기록도 보존한다.

## 2. 구현 범위

- 고객 온보딩: 실제/DEMO 구분, 담당자·연락처·사업 목표·AEO 목표·직원·확인 근거.
- 의료·법률·커머스·일반 브랜드 프로필. 확인되지 않은 자격, 성능, 후기 등은 초안에서 확인 필요로 남긴다.
- 10단계 프로젝트 상태와 근거 검사. 단계 건너뛰기 차단, 변경 이력, 세 소비자 플랫폼 Baseline/Follow-up 계획 연결.
- 기존 진단 과제를 실행 전략으로 전환. 관측 사실·근거·가설·대상 페이지·작업 지시·검증 방법 분리.
- 템플릿 기반 8가지 초안, 불변 버전 이력, 최신 버전 고객 승인 기록, 의료·법률 검토 기록. 수정 시 재승인과 재실행 필요.
- 7가지 실행 상태, 담당자·기한·작업 시간·전후 증빙·완료 내용·재측정 기록. 외부 홈페이지 자동 게시 기능은 없다.
- 초기 진단/실행 전략/월간 성과/개선 전후 HTML 보고서. 생성 시점 원본 및 SHA256 보존, 최종 승인, 브라우저 인쇄/PDF 저장.
- 영업 파이프라인·계약 기간/범위/갱신, 청구·입금·원가 수정 이력, 시간 기반 직접 원가와 기여이익. 미입력 금액은 null이며 0원으로 추정하지 않는다.
- 확인 근거가 있는 수동 유입·상담·예약·구매 자료만 보고서에 집계. 자동 전환 분석 도구 연결은 없다.
- 직원 로그인, OWNER/MANAGER/ANALYST/VIEWER, 프로젝트 범위, 접근/중요 변경 기록. 비밀번호는 scrypt, 세션은 난수 쿠키와 서버 해시로 저장한다.

## 3. 데이터베이스 변경과 보존

추가 전 `data/backups/stage5-db-before-*.json`에 기존 관계형 데이터를 백업했다. `Project.operations`와 `Report.payload` JSON 열, `StaffUser`, `StaffSession`, `AccessEvent` 테이블만 추가했다. 기존 응답 원문·분석·질문·진단·과제를 삭제하지 않았다. 실행 작업의 추가 정보는 기존 Task payload를 사용한다. 마이그레이션은 `prisma/migrations/20261008_stage5/migration.sql`, 기존 설치용 실행기는 `scripts/migrate-stage5.mjs`다. 인증 관련 데이터 때문에 5단계는 PostgreSQL이 필요하다.

백업은 민감한 내부 자료다. Git에 추가하지 않고 접근 제한된 별도 저장소에 정기 백업해야 한다. JSON 백업은 자동 복구/재해 복구 시스템을 대체하지 않는다.

## 4. 화면과 접근 경로

`http://127.0.0.1:3000/login`에서 최초 OWNER를 사용자가 직접 등록한다. 기본 비밀번호는 만들지 않았다. 로그인 후 기존 메뉴와 다음 메뉴가 함께 제공된다.

| 메뉴 | 사용 |
| --- | --- |
| AEO 운영 관제실 | 실제 고객 기본 필터, 상태별 건수 클릭→고객 목록 |
| 고객사 운영 | 온보딩, 업종별 증빙, 프로젝트 시작·상태·측정 계획 연결 |
| AEO 실행 관리 | 진단→초안→수정 버전→고객 확인→완료 증빙·시간 |
| 고객사 보고서 | 원본 생성·승인·HTML/PDF, 확인 가능한 전환 자료 |
| 영업·계약 관리 | OWNER 전용 파이프라인·계약 관리 |
| 수익성 관리 | OWNER 전용 청구·입금·직접 원가·미입력 구분 |
| 직원 권한·이력 | OWNER 전용 계정·범위·접근 기록 |

MANAGER는 배정 프로젝트의 운영·승인을 관리한다. ANALYST는 배정 자료 분석·수정안 작성·보고서 초안 생성이 가능하며 연락처·계약 상세·원가는 숨긴다. VIEWER는 배정된 최종 승인 보고서만 조회한다. 프런트엔드 메뉴와 서버 API 모두 권한을 검사한다. 직원 권한/비밀번호 변경 및 비활성화 시 기존 세션을 폐기한다.

## 5. 테스트

`tests/operations.test.ts`는 업종 템플릿, 확인된 사실만 사용, DEMO 유형 불변, 버전 충돌, 고객 승인·규정 검토, 미승인 실행 차단, 재승인, 단계 증거, null 원가, 검증된 전환, HTML 이스케이프와 해시, 비밀번호/범위/민감정보 제거를 검증한다.

`tests/e2e/operations.spec.ts`는 홍제 A치과·서울 B법무법인·C브랜드 고체방향제의 **DEMO 프로젝트** 각각에서 등록→질문→3플랫폼 Baseline→DEMO 진단→수정안→가상 고객 승인→작업 완료→Follow-up→승인 보고서를 실제 PostgreSQL과 브라우저로 검증한다. 다른 고객의 청구 수정, 직원 역할/프로젝트 범위, VIEWER 초안 접근, 익명 접근, 계정 비활성화, 승인 보고서 원문 불변도 확인한다. DEMO 완료 기록은 실제 고객 수주·승인·홈페이지 게시·AI 성과가 아니다. 테스트 프로젝트와 격리된 테스트 계정은 종료 후 제거한다.

실행 결과와 현재 데이터 보존 대조는 `docs/STAGE5-VALIDATION.md`에 기록한다.

## 6. 미구현·미검증

실제 고객 승인, 공개 사이트 수정, 실제 소비자 AI 관측/성과, 실제 매출/예약 전환은 이번 DEMO 시험으로 검증되지 않았다. 고객 승인 기능은 직원이 실제 고객의 승인 증빙을 기록하는 방식이며 고객 전자서명 포털은 아니다. 의료·법률 규정 검토 체크는 검토자의 기록이며 자동 법률 적합성 판단이 아니다.

홈페이지 진단은 기존 HTML/기술 검사 범위다. 전체 JS 렌더링, 자격 진위, 실제 색인 및 AI 추천 원인의 검증을 보장하지 않는다. 템플릿 초안은 사람이 최종 작성·사실 확인해야 한다. 고급 회계, 비용 기간별 배분, 분석 도구 자동 연결, 외부 게시, AI 자동 초안, MFA/계정 복구는 후속 범위다.

## 7. 유료 AI 호출

이번 단계의 API 관측 호출은 **0회**다. `LIVE_AI_ENABLED=false`, `FREE_GEMINI_ENABLED=false`를 유지한다. 키가 존재해도 유료 실행 경로는 서버에서 차단한다. 테스트는 DEMO/모의 어댑터만 사용하며 기존 비용 차단 테스트도 실행한다. 수익성 입력의 API 원가는 직원이 입력하는 내부 기록이며 외부 호출을 실행하지 않는다.

## 8. 실행 방법

현재 PC의 `.env`를 덮어쓰지 않는다. DB가 꺼졌을 때만 별도 터미널에서 시작한다.

```powershell
node scripts/local-postgres.mjs
```

앱 터미널:

```powershell
node node_modules/prisma/build/index.js generate
node node_modules/next/dist/bin/next build
node node_modules/next/dist/bin/next start --hostname 127.0.0.1
```

개발 서버는 `node node_modules/next/dist/bin/next dev --hostname 127.0.0.1`이다. 기존 설치에 스키마가 없다면 백업 후 `node scripts/migrate-stage5.mjs`를 한 번 실행한다. DB 초기화 명령은 사용하지 않는다.

검사 명령:

```powershell
node node_modules/typescript/bin/tsc --noEmit
node node_modules/vitest/vitest.mjs run
$env:AEO_TEST_POSTGRES='1'
node node_modules/vitest/vitest.mjs run tests/postgres.integration.test.ts
Remove-Item Env:AEO_TEST_POSTGRES
node node_modules/@playwright/test/cli.js test
```

Playwright는 Edge와 별도 3100 포트, 격리된 테스트 인증 영역을 사용한다. 실제 OWNER를 만들거나 실제 비밀번호를 변경하지 않는다.

## 9. 실제 첫 수주 전에

OWNER 비밀번호와 직원별 프로젝트 범위를 설정하고 승인 근거 보관 절차를 정한다. 실제 고객은 DEMO와 별도로 등록한다. 의료·법률 표현은 관련 자격·광고 규정 검토를 받는다. 범위/납품물/표본과 한계/고객 승인/작업 권한을 계약에 명시한다. 현재 임시 개발 PostgreSQL을 영속 저장소와 정기 백업·복구 검증 체계로 전환한다. 내부 도구는 localhost에 바인딩하며 공개 서비스로 배포하지 않는다.

## 10. 6단계 우선순위

1. 영속 PostgreSQL, 암호화 백업/복구 시험, MFA·계정 복구와 감사 이력 강화.
2. 실제 수주 고객 1개에서 근거 검토·승인·게시 확인·동일 조건 반복 관측의 운영 검증.
3. 고객 승인 포털과 허용된 분석 도구의 읽기 전용 유입·전환 연결, 원가 기간별 분석.
